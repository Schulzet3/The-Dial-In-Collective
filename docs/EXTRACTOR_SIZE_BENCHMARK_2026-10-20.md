## Exact evidence

- [First controlled run 39368679767](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/39368679767): **14 URLs**, 11 parsed at 900 KB versus 12 at 2 MB.
- [Expanded controlled run 39368880810](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/39368880810) at [study code SHA `1d5c1da7`](https://github.com/Schulzet3/The-Dial-In-Collective/commit/1d5c1da7efdd1387f674ec1f0ba4396ed57cb1ba): **20 URLs**, 19 accessible, 1 unavailable; **16 parsed at current 900 KB vs 17 at 2 MB**, with 1 additional coffee recovered. Both remained ambiguous on the generic Mango Tree store HTML and deliberately rejected the Queen City homepage negative control. No increase in field keys on the already-accepted under-900 KB pages.
- **Actual incremental coffee:** Picky Chemist Gesha Village page was **1,216,190 bytes**. The current 900,000-byte response bound rejects it; a temporary 2,000,000-byte copy extracted **7 supported fields**: name, roaster, origin, process, producer, variety and elevation. Neither roast nor tasting notes were automatically asserted. The page reduced to 59,448 bytes after stripping nonsemantic scripts/styles, retaining **exactly the same extracted fields**.
- **17 of 17 successfully parsed coffees kept identical extracted field values after test-only script/style/comment removal**; this is encouraging but **not proof** for all merchants or formats. In the expanded run, median of per-page repeated parse times was **6.07 ms original vs 4.16 ms stripped** (about 31% lower). Picky on that run was **7.16 vs 2.55 ms**, and approximate retained/allocated heap delta **3.83 MB vs 1.21 MB**. Memory and duration are runner-specific proxies, not Netlify billing.
- **First 256 KB only** matched the full extracted field set for **13 of 17** parsed products, but missed later information on PERC Mara, PERC Franky, Onyx Mullugeta and Tim Wendelboe Gachatha. Do **not** make prefix-only extraction the sole source of product details. Potential future use: tentative fast preview with guaranteed full-page fallback; not implemented.
- **Compression**: nine public HTML pages returned successfully when asking for gzip/Brotli using an isolated transport copy. Observed transmitted-body reductions ranged **75.77% to 87.99%** (median about **80.36%**). Picky: 1,216,190 decoded bytes, **213,310 transmitted bytes**, identical HTML and identical extracted product fields. Mango: 662,738 decoded, **146,402 transmitted bytes**, identical storefront HTML (still not a selected coffee). The eight product pages with parsed HTML retained the same extracted fields across identity/compressed responses; some pages had dynamic HTML differences. This does not prove lower hosting costs, and decompressed size still MUST be bounded.
- **Four public platform endpoints** also parsed without passwords: Mango Tree Ecwid (5 fields), PERC Shopify Ajax (3), Sweet Bloom Shopify Ajax (2), Park City Woo Store (3). These smaller exact-product endpoints often make extraction possible even if a large storefront shell is ambiguous. But PERC had **9 fields in its full HTML** and Sweet Bloom **8**, so indiscriminately replacing the full page with API-only facts would lose real evidence.

## Method and attribution

`scripts/audit/coffee-extractor-2mb-study.mjs` copied all trusted `src/server/*.mjs` modules **only to a disposable GitHub Actions runner temp directory**. The 2 MB copy changed `MAX_HTML_BYTES` from 900,000 to 2,000,000 and its two parser character guards from 1,000,000 to 2,000,000. An independent optional compressed copy changed `Accept-Encoding: identity` to `gzip, br`. The source SHA256 hashes were compared before and after and unchanged. Production modules were not edited.

For comparability, each public product URL was fetched **once with the isolated 2 MB guard**; if its decoded HTML was over 900,000 bytes, the 900 KB result was classified `page_too_large` under the existing guard, otherwise parsed three times by the unchanged real parser. The isolated 2 MB parser received the *same* HTML and three parse measurements. The experimental 256 KB prefix and stripped HTML were derived in memory only; no raw page was saved to disk or GitHub. Compression required a **separate network request**, so a dynamic page or network latency could change between samples. CPU and heap numbers are approximate local-runner measurements; no Netlify per-invocation usage/credits were estimated. One URL was unavailable; this is **not** proof that it lacks metadata.

## Ranked next options (proposals, not shipped)

1. **Best next coverage gain: adaptive 2 MB retry for verified product-shaped URLs only.** Keep 900,000 bytes as the normal bound; when a specific validated product page is rejected solely for size, allow **one** DNS-pinned HTTPS retry capped at 2,000,000 decoded bytes, subject to total elapsed-time/redirect guard. Require matching product identity before accepting facts. This recovers Picky in this sample and limits maximum untrusted input for ordinary browse/homepage URLs. It still costs a second request on oversized cases and needs guard/decompression-bomb/SSRF/latency tests. **No owner approval to implement or deploy this change has been given.**
2. **Large bandwidth opportunity: request gzip/Brotli with a strict *decompressed* cap and anti-zip-bomb tests.** Existing transport already knows how to decode gzip/deflate/br; the isolated study changed only the request header. Test malformed encodings, dynamically changed pages, decompression failures, content-length behavior, and fallback to identity before shipping. Faster network transfer is plausible; Netlify credit savings are **unverified**.
3. **Safer parser optimization: optional in-memory removal of non-product scripts/styles/comments while preserving all `application/ld+json` Product blocks.** 17/17 facts matched here, median parsing time was lower, and Picky's resulting text was just 59,448 bytes. The fetch still must respect its **decoded** transport cap. Before shipping, add regression fixtures with non-JSON-LD embedded merchandise state, blend/release/recipe descriptions, multilingual pages, malformed tags, and full source-to-field equality; fall back to original content if needed.
4. **Platform-aware exact-product API + full-page supplement**: Ecwid first for the grounded Mango Tree `-p` product; Shopify/Woo's no-token public JSON should supplement HTML when it has fewer facts, not replace rich on-page roast/process/story/espresso guidance. This is substantially **already implemented in unpublished development code**; expand real-source test matrix rather than duplicate modules or invent roaster-specific values.
5. **Header-first progressive preview only with mandatory full-evidence retry**, not a standalone extraction strategy. Four of 17 parsed sources lost supported fields when capped to 256 KB.
6. **Potential later studies**: canonical `product` JSON-LD and microdata scope, robust JSON-LD `@graph` matching, WordPress public storefront variations, server-side product-only cached read-through keyed by URL plus release identity, and controlled backoff on intermittent 403/429s. These were **not measured here**; do not imply the app supports them or that scraping blocked merchants would be permitted.

## Existing security and production boundary

The **actual deployed** `src/server/coffee-url-guard.mjs` remains at **900,000 bytes**. Its production request uses HTTPS with TLS certificate verification, pinned global IPv4 DNS at connect time, rejects private/reserved/credentialed/IP URL targets, validates each of at most two redirects, has a ~10s socket/11s fetch timeout, and does not execute remote JavaScript. Supabase admission, 12 per 24h account previews, >=30-second cooldown, RLS and saved history are untouched. Never disable these protections merely to improve coverage.

A bounded 2 MB cap is **not** a permission to follow arbitrary internal links, run third-party scripts or open merchant admin APIs. No production SQL, Edge, Netlify deploy, data edit or credit-bearing sandbox branch was created. Independent Netlify project read confirms old READY/current deploy `6ad6801b20c067ef4f2e3729`. **Owner decision still needed** before *any* changed fetch-size, compression or pre-parser policy is implemented or released.
