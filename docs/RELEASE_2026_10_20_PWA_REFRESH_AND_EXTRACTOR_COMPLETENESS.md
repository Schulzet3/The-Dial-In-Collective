## Root cause and solution: installed app may be stale despite new Netlify READY

- **Verified in source:** prior `scripts/pwa/service-worker.template.txt` used cache-first for navigation and static files, and its install deliberately did **not** call `skipWaiting`. Long-open iOS Home Screen or browser clients could stay on old CSS/JS/HTML after a server-side READY deployment. This is a proven stale-app design path, **not direct proof that the owner's particular phone used that path**; we cannot inspect their device cache from these tools.
- **Implemented in [f8c94d9](https://github.com/Schulzet3/The-Dial-In-Collective/commit/f8c94d99bf381a0a6fdbeba17fd48c20a8f4f2da):** atomic public shell precache followed by `skipWaiting`, network-first public HTML **with offline cached fallback**, register/update check when reopening/foregrounding; no force-reload that could discard draft forms, offline shot outbox, owner cache or local authentication. Static revisioned shell assets remain cache-first and private/API/admin destinations are not stored. The first launch after deploy can still need close/reopen or refresh to switch old controllers.
- The single approved Autofill button is now **100% width, 56 px minimum height, 16 px bold**, with existing color/form/behavior retained. Previous 46 px/14 px styling was too close to normal controls to be obvious. Button CSS, state, submit behavior and no unapproved design changes covered by [UX tests](../tests/ux-refinements.test.mjs).
- **Browser/visual evidence:** [private visual review](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/39479766224) PASS, [UX 390 px Playwright, synthetic access regression](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/39479766253) PASS and [app/Node/lint/build](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/39479766190) PASS at the UI-changing commit.
