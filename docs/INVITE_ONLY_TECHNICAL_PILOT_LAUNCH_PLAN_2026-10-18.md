## Existing invite controls and launch bottleneck

**Read-only hosted check 2026-10-18:** `private.beta_members` has **2 enabled/admitted** member accounts; `private.beta_invites` has **0 currently usable tokens** (past 2 issued/redeemed). An invited email-confirmed user can already sign up, authenticate and redeem a token using member-gated `dic_redeem_invite` -> `private.redeem_beta_invite`, backed by SHA-256 **token hashes**, server-side expiry/revocation/max uses, rate limiting and row locks to prevent double redemption. No public access to private invitation storage.

Admin site currently has a read-only dashboard, **no UI to issue, revoke or replace invitations** ([#24](https://github.com/Schulzet3/The-Dial-In-Collective/issues/24)). For a very small **owner-approved** pilot, one optional fastest path is **explicitly owner-authorized operator issuance of a handful of high-entropy, single-use, short-expiry tokens**, storing **only SHA-256 hashes** in `private.beta_invites`, delivered privately to the owner exactly once (never GitHub, public logs or member-facing Community). Existing server revocation/expiry works; owner must have an agreed secure path to revoke/rotate operator-managed tokens. This avoids delaying a five-member technical pilot for the complete admin UI, but does not close #24 or provide self-service invite controls. Alternative is implement and test safe admin issue/revoke/replace UX (#24) before the launch; this would add a separate backend migration to the release. **Neither path is approved or executed yet. Do not create fake accounts, live invites, send mail, or relax the invite gate without the owner approving it.**
