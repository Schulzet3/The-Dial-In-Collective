## Canonical reason and user-facing rule

A member may add any real coffee to their **personal** library with two required facts, Name and Roaster. The member may paste an HTTPS URL, review suggestions, correct errors, fill gaps, and click **Add Coffee**, then immediately Log Shot → Rate → Recommendation. **No admin approval is required for that personal action.** A publicly shared **Verified** coffee has a higher trust threshold: exact official roaster/coffee/harvest or uniquely compatible canonical evidence. A member's confirmation is a useful personal fact confirmation, **not independently sufficient to amend public community facts**. Trusted official-source verification occurs automatically where evidence supports it; otherwise a new nonadmin coffee is usable privately as Pending. Existing roaster aliases, URL/release cross-checks, confirmed fuzzy matches, original shot IDs and audit requirements remain Locked and unchanged.

## First real Wuri browser test: JWT role compatibility incident and targeted SQL fix (2026-10-16)

**Observed FAIL before correction:** Owner, while genuinely signed into the existing confirmed and admitted nonadmin account `schulzet3@gmail.com`, pasted `https://sweetbloomcoffee.com/products/wuri` and received `Sign in with an admitted beta account to check URLs.` Read-only database confirmed both accounts were admitted and the reported one was confirmed/nonadmin. Netlify observability independently recorded the user request `POST /api/coffee-preview` at `2026-10-17T01:49:50Z`, **HTTP 503**. The failed preview did not prove the roaster's public HTML was bad and did not create a coffee or shot.

**Exact reproduced cause:** The new `public.dic_claim_universal_preview()` SQL used `current_setting('request.jwt.claim.role',true)='authenticated'`, but real PostgREST may populate only `request.jwt.claims` JSON. The underlying `auth.uid()`, `auth.role()` and `dic_session_status()` already support JSON-claims fallback, so a real admitted member could get a true app status but a spurious API claim denial. Reproduced on production with a **BEGIN/ROLLBACK, JSON-claims-only** execution where member session status was true, `auth.role()='authenticated'`, and the old wrapper falsely returned `admitted_member_required`.

**Fix deployed — SQL ONLY, no new Netlify production build/credits:** Additive migration `supabase/migrations/20261017020000_dic_universal_preview_claims_json_auth.sql` changes only the authenticated role check inside `public.dic_claim_universal_preview()` to **`auth.role() is distinct from 'authenticated'`**, preserving `auth.uid()`, `private.is_member()`, confirmed-email check, separate public function grants, and shared 30-second/60-daily quota. For isolated CI, `tests/sql/bootstrap.sql` now models Supabase's actual `auth.role()` behavior, and `supabase/tests/universal_url_preview.sql` adds an explicit **JSON-only JWT admitted user** positive + immediate cooldown negative. Isolated SQL run `38992902344` **PASS**, application CI run `38992902373` **PASS**; Supabase production migration `dic_universal_preview_jwt_role_compat` **SUCCESS**. Production rollback-only post-fix auth simulations for **both genuine admitted accounts** PASS, with immediate 30s repeat denial and anonymous role denied; no data changes committed. The prior independently published Netlify deploy `6ad2c872ad7a8fa78dc410dc` is still the active website; no new frontend release needed.
