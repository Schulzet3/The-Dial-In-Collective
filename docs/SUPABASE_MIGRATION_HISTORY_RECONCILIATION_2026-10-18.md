## Independent authoritative evidence

- Read-only `supabase_migrations.schema_migrations` returned **28** applied version/name records and their stored SQL `statements[1]`. Computed true Git blob SHA-1 from **`'blob ' + byte length + NUL + SQL bytes`** in PostgreSQL `pgcrypto.digest`, and matched that against the GitHub tree blob SHA-1. Same-source bytes, not merely similar textual intent; no statements were executed as DDL.
- Original comparison: **26/28 exact SQL bytes**; remaining two existing files differed only by one extra trailing LF. **Seven** of the exact SQL blobs had historic GitHub filenames/versions different from the hosted migration records. We independently fetched and inspected all seven actual bodies and confirmed perfect byte identity before changes.
- [Reconciliation commit `0184d94a`](https://github.com/Schulzet3/The-Dial-In-Collective/commit/0184d94a88834d03437cf86bc7a0a33792efc181) renamed exactly seven files to actual hosted version/name, retaining **identical Git blobs**, and removed one extra final LF each from `20261014152014_dic_owner_only_import_exception.sql` and `20261014200634_dic_setup_rename_feed_memory.sql`. No application SQL logic, table, record, privilege or backend behavior changed. All historical versions remain recoverable in Git.
- **Independent post-reconciliation recheck PASS: 28/28 hosted applied migration version/name/SQL-byte hashes now match 28/29 GitHub migration files exactly.** The sole additional GitHub file is **unapplied** `20261018221843_dic_community_release_context.sql` for the future separately approved Community release.

## Deploy and remaining limits

**The original seven history divergences are resolved.** A read-only, live **Supabase CLI linked remote `migration list`/`db push --dry-run` was NOT run**, because this workspace has no prelinked production database password. Matching 28/28 history SQL and names is stronger source integrity evidence than filename-only CLI output, but does not establish *all* provider configuration parity or grant live DDL authority.

For a separately approved Community SQL update, the pending new migration is [`20261018221843_dic_community_release_context.sql`](../supabase/migrations/20261018221843_dic_community_release_context.sql). Any provider `apply_migration` action may assign its own version; after successful **authorized** application, re-read hosted version/name/SQL blob SHA, **align the pending GitHub filename/name to the actual hosted record without altering the SQL bytes**, refresh this attested manifest and CI, and only then authorize/publish the Netlify frontend. Do **not** run blind `db push` just because historical parity was repaired. Supabase CLI `db push --dry-run` is preferable for final confirmation if trusted linked access is available; `apply_migration` may be used narrowly with the version reconciliation described in the [runbook](COMMUNITY_RELEASE_GROUPING_PRODUCTION_READINESS_2026-10-18.md).
