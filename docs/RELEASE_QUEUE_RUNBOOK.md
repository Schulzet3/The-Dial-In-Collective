## Release batch and controller
- Default release candidate = one **combined exact tested development source SHA**, including all source-merged `READY` features. A clean `docs/RELEASE_QUEUE.json` and actual merged test evidence are part of readiness. An incomplete PR not merged into development does **not** contaminate a batch, but an incomplete change already merged **does block** the whole batch.
- The main one-use release controller independently reads the queue from that tested source SHA and diffs it against the **last actually published tested application SHA** from the consumed ledger. It refuses `README`-only/no deployable changes; an untracked app file; an incomplete merged feature; invalid/missing queue entries; a stale baseline or any mismatch in Git ancestry. It also verifies the existing one-use grant/CI, migration backup risk, and credits. GitHub private Free status checks are advisory, not enforced by GitHub branch protection.
- One user instruction to **publish** authorizes one reviewed scope-bound batch; the assistant performs normal preflight, only approved backend steps, one nonforce single-use Netlify release and postflight, recording actual prod SHA, migrations/Edge, history/count invariants and queue `DEPLOYED` with receipt. **No owner-device signoff** is required for deployment completion. User-reported bugs start tracked follow-up work.
- If owner wants only part of a batch but unready/other app code is already merged, DO NOT silently publish the entire development tip. Build an explicitly scoped and reviewed candidate using a safe Git strategy, then run all exact-SHA CI and the same source-coverage controller checks. Do not imply a cherry-pick is already available or approved.
- **Release readiness ≠ production deployed.** A READY item is fully prepared to the limit possible before publication; hosted SQL/provider migrations, actual Netlify READY readback and credit bill remain unverified until performed. Additional encrypted backups are required only for potentially destructive DB work; the existing approved automatic backup request can be used without another owner pause, but ciphertext/offsite success must be observed before destructive work.

## Machine-readable queue (schema v1)
`docs/RELEASE_QUEUE.json` is canonical for release grouping; GitHub issues/PRs retain discussion and testing facts.
- `published_base.tested_source_sha` must equal the latest `docs/RELEASE_CONSUMPTION.json` source, not a development commit or a Netlify artifact SHA.
- Each item: unique `DIC-Q-<issue>` ID, `issue`, `pr` optional, descriptive `title`, `state`, `merged_source_sha` (or null before merge), **exact affected deployable filenames** in `scope_paths`, `tests`, numeric `ci_runs`, `blockers`, and `owner_source`. Record no credentials or raw member data.
- `READY` requires a merged SHA actually ancestral to the release candidate, tests/CI evidence and zero blockers. `IN_PROGRESS`, `TESTING` and `BLOCKED` cannot be shipped if already merged. `DEPLOYED` is a historical receipt not a new ready item.
- Commands: `node scripts/release/release-queue.mjs --validate` verifies schema; `--status` prints a read-only queue/candidate assessment, including blockers, without publishing or failing merely because unfinished work is tracked; `--strict` fails on anything not ready, intended for guarded release preflight. GitHub Actions runs schema+status on every development push/PR; full Node suite tests false-ready, cross-account changes and untracked changes. Batch controller on `main` adds the strict gate before consuming a grant.
- After successful production postflight, update the queue baseline to the new verified published *tested* app SHA, move delivered items to `DEPLOYED` with real release/Netlify receipts, and preserve historical items in `history`. Do not silently drop prior entries or conflate READY with ACCEPTED.
