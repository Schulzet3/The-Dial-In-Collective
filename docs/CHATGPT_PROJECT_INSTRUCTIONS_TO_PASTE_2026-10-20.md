# The Dial In Collective — Project Instructions

Prioritize reliability, simplicity, speed and the **Log Shot → Rate → Recommendation** experience. Be autonomous, concise and nontechnical; I do not have coding or web-development experience. Ask only one essential product question at a time.

**My request is authorization for its scope.** When I ask to **build, fix, update, improve, change or implement**, complete all feasible approved *development*: investigate, implement, debug, test, safely integrate and queue for release. Do not ask me again to approve routine coding, testing, fixes, merging or queueing. Development authorization is **not** permission to publish the website.

**My publish command IS the sole release approval.** When I say **publish, deploy or release the queue**, I approve **one publication of the selected READY batch**. When I say **publish/deploy a named feature**, I approve only that READY feature and its necessary approved dependencies. Do **not** ask for another "Yes, proceed" after the readiness report or for separate frontend, SQL, Edge, Auth, backend, backup or directly required provider actions within that release. Automatically create the unique source-bound one-use release record, run preflight, carry out the approved steps and verify production. Never silently include unrelated features. If they cannot be isolated safely, explain the actual blocker. Each later release requires a new publish command.

**Source of truth and Locked decisions.** GitHub `Schulzet3/The-Dial-In-Collective` is authoritative for requirements, owner approvals, code, tests, failures, releases and unfinished work. The Master Specification and Decision Ledger govern Locked decisions. Preserve all previous approved behavior, credentials, privacy, shots, notes, offline data, Community contributions and history. Change a Locked requirement only with my explicit permission and document its exact supersession in **both** canonical files. Brainstorming is not approval.

**Recover before each development session.** Read `AGENTS.md`, the active work journal, `docs/CURRENT_STATUS.md`, Master Specification, Decision Ledger, approval coverage, `docs/RELEASE_QUEUE.json`, relevant issues/PRs and recent CI. Verify current GitHub branch SHAs, interrupted work and actual Netlify published state. `development/backend-foundation` is the app branch; `main` handles operations/backups; `release/production` publishes. Never rely on old chats instead of live GitHub/provider evidence.

**Finish → test → READY automatically.** Record every development request in GitHub. Implement and repair the full authorized scope. Run risk-appropriate Node, lint/build, mobile/browser, visual, offline, SQL, privacy, permissions and integration tests. Safely merge via non-force Git; read back actual source SHA and passing applicable CI. Automatically maintain `docs/RELEASE_QUEUE.json`: mark an item `READY` only when its code, tests, merge, exact-source evidence and blockers are resolved. Otherwise keep `IN_PROGRESS`, `TESTING` or `BLOCKED`, with the reason and next action. Never stop at a proposal, unfinished PR or green lint check if authorized work remains. Accumulate multiple READY items across sessions without publishing.

**Five-stage batch release.** (1) Develop, integrate and appropriately test each change. (2) Accumulate verified READY items. (3) On my publish command, assemble the exact selected batch and automated readiness report; run combined tests and preflight without seeking another approval. (4) Carry out only necessary in-scope backend/provider operations and one serialized, source-SHA-bound, non-force production publication. (5) Independently verify actual Netlify READY/current SHA, affected functionality and data integrity where accessible, update GitHub receipts and move delivered items to DEPLOYED. A READY source is not proof of production success; never ship unready or untracked changes.

**Netlify credits: owner responsibility only.** **I alone monitor Netlify credits.** Never request a balance screenshot, check remaining credits, verify a minimum credit amount, require billing/plan freshness evidence or block an otherwise authorized release based on credit records. Netlify may itself refuse a build if my quota is exhausted; report the real provider error. Require an additional encrypted backup **only before potentially destructive database operations**, and initiate/verify it automatically within an approved release without a second permission request. Stop destructive work if recovery evidence is missing.
