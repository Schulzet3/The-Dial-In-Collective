# The Dial In Collective — offsite recovery and release runbook

This operational guide supplements, and does not replace, the Locked Master Specification and Decision Ledger. Never copy database passwords, age private recovery identities, GitHub tokens, Netlify API keys, or downloaded user datasets into this repository.

## What nightly encrypted Drive archives contain

GitHub Actions on `main`, `.github/workflows/nightly-backup.yml`, schedules the Supabase PostgreSQL 17 dump at **09:23 UTC daily**. It connects using the GitHub Actions secret `SUPABASE_DB_URL` (session-pooler URI, TLS required), encrypts with the **public** `BACKUP_AGE_RECIPIENT`, and retains ciphertext in private GitHub Actions for **30 days** as a second independent recovery location. The standalone Google Apps Script courier reads eligible artifacts. The courier watches successful scheduled or manually dispatched `main` workflow runs (not test `push` runs) and places the ciphertext ZIP in the owner's private `DIC Automated Encrypted Backups` Google Drive folder. It is configured to retain approximately 30 days of Drive artifacts (minimum two latest), and send stale-transfer and execution-error emails.

**Backup v1 bundle** contained `database.dump`, `toc.txt`, `storage-object-count.txt`, `manifest.json`. From the source-inclusive backup update, subsequent bundles additionally contain **`app-source.tar.gz`**, a checkout of `development/backend-foundation` that includes current app source, UI, calculation engine, SQL migrations, test code, recovery scripts, Netlify build manifest, and nonsecret documentation. The bundle's manifest includes the source commit ID and source archive SHA-256. All contents are encrypted before leaving the GitHub runner; the age **private** SSH Ed25519 recovery key exists only on the owner's Mac and separate secure offline location.

The backup job intentionally **fails closed** if Supabase Storage contains file objects, because PostgreSQL alone preserves only Storage metadata, not file bytes. At initial verification, Storage object count and bucket count were zero.

## What a database/source archive does NOT capture

- Supabase's dashboard project settings, SMTP provider login/secrets, provider-managed OAuth/JWT signing material, site/redirect URLs, dashboard rate limits, or the encryption key itself.
- Netlify account/site ownership and site-level environment settings, GitHub repository permissions, action secrets/variables, OAuth connector authorizations or Google Apps Script trigger configuration.
- Any future Supabase Storage object bytes unless a separate download+restore path is deliberately added.
- Original iPhone/Mac prototype data not imported into cloud. Preserve the previously downloaded prototype and reviewed JSON backup files independently.
- A guaranteed one-click restore into hosted Supabase. The raw `pg_dump` archive includes Supabase-managed internals and may need provider-specific restore processing.

## Configuration inventory to recreate after a disaster

1. Private repository source: restore `app-source.tar.gz` to a **new private GitHub repository**; keep review/branch workflow and commits separately if available. Do not commit personal exports.
2. Supabase Free: recreate project, apply checked-in `supabase/migrations/` in correct version order; recover user/application/auth data through a supported Supabase/Postgres migration path. Recreate Auth settings, allowed redirects, password policy, email confirmation, custom SMTP (if configured), and invitation/member policies. A different JWT signing key will require users to sign in again; never restore old refresh tokens blindly.
3. Netlify: connect private GitHub branch `development/backend-foundation`, Node 22, `npm test && npm run build:cloud`, publish `dist`, site origin `https://the-dial-in-collective.netlify.app`, and add only public `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` to the build environment. No database passwords or service-role keys in the browser build. Keep visitor SSO restriction until explicit beta release approval.
4. Backup continuity: configure the GitHub Actions `SUPABASE_DB_URL` secret, `BACKUP_AGE_RECIPIENT` public variable, and owner-authorized private Apps Script Script Properties `DIC_FOLDER_ID`, `DIC_ALERT_EMAIL`, `DIC_GITHUB_ACTIONS_READ_TOKEN`; install the three-hour polling trigger. New credentials should be generated securely on each restored service.
5. Run the Auth/user/isolation tests and a test restore into disposable infrastructure **before** making the recovered app writable.

## Low-maintenance operational recovery

1. If Google Drive fails: locate the last successful encrypted `dic-encrypted-nightly-*` GitHub artifact; it remains available for 30 days for new runs. Investigate Apps Script `Executions` and `DIC_GITHUB_ACTIONS_READ_TOKEN`, and rerun `syncPrivateBackups` once connectivity is repaired. Do not turn off encryption or export private auth tables as plaintext.
2. If GitHub fails but Drive works: obtain the newest Drive encrypted ZIP, securely decrypt using the owner-held private recovery key and verify `manifest.json` checksums. It includes a source tarball in v1+ source-inclusive archives. No cloud service ever stores the private key.
3. If Supabase must be rebuilt: provision a new Supabase project, apply the recorded migrations, restore app and Auth rows with the supported Supabase migration procedure, regenerate backend secrets, configure Auth redirects/password policy/SMTP, redeploy the private Netlify app and run owner-bound security tests. JWT rotation can require users to sign in again; do not restore refresh tokens blindly.
4. Do not enable historical import, public signups or email beta solely because the dump can be decrypted: independently verify the needed hosted Auth, RLS, app mutations, alerts, and recovery path. Revisit backup design **before** adding Supabase Storage objects, as the current exporter deliberately fails closed when any are present.

## GitHub Ubuntu 26 migration mitigation and verified recovery hardening — 2026-10-13

GitHub's [runner-images issue #14748](https://github.com/actions/runner-images/issues/14748) warns that `ubuntu-latest` moves from Ubuntu 24.04 to 26.04 in phases starting **October 19, 2026** (target completion November 19). This advisory was **not** a backup failure: owner's manually dispatched main backup [38478825183](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/38478825183) passed.

**Implemented:** The `nightly-backup.yml` and `database-recovery-drill.yml` workflows on **both** `main` and `development/backend-foundation` now explicitly run on `ubuntu-24.04`. This avoids unreviewed OS-major-version changes; GitHub still patches the Ubuntu 24.04 runner image over time. Dev encrypted backup [38479304768](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/38479304768) succeeded on Ubuntu 24.04, demonstrating current encryption and archive tooling compatibility.

**Recovery startup race found and fixed:** The first Ubuntu-24.04 dev recovery run [38479310631](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/38479310631) failed at local PostgreSQL startup (`database system is shutting down`). Inspection of the official Docker PostgreSQL entrypoint showed that initial database setup briefly starts a **Unix-socket-only temporary server**, then stops it before launching the final server. A Unix-socket `pg_isready` probe can succeed during that temporary window and race shutdown. Both dev and main `scripts/backups/isolated-recovery-drill.sh` now probe **TCP 127.0.0.1 inside the `--network none` container**, which becomes ready only when the final instance starts; failed startup also captures limited container logs. This adds no externally accessible port or plaintext artifact.

**Verified:** Development recovery rerun [38479513765](https://github.com/Schulzet3/The-Dial-In-Collective/actions/runs/38479513765) **passed** on Ubuntu 24.04, restoring **all 35 first-party application/private tables and core Auth users/identities**, with matching row counts and no hosted database changes. Production `main` now contains the same hardening and OS pin; its **first post-change scheduled/manual production run has not yet executed** and must not be described as passed. Managed-Supabase configuration restore remains a separate, unverified release gate. No Locked requirements, historical import gates, stored credentials, or local prototype data were changed.

**Future review:** Keep the explicit runner label during beta. Trial Ubuntu 26.04 only in isolated development backup/recovery tests and promote to `main` after success; revisit the pin before Ubuntu 24.04 runner support ends.
